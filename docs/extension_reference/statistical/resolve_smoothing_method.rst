resolve_smoothing_method
========================

.. math::

   \text{requested method}\longmapsto\text{normalized fitting criterion}

The requested spelling can represent a family-dependent policy rather than a literal criterion. ``auto`` prefers an available REML backend, then UBRE/AIC with known scale, then GCV, and finally fixed smoothing. GCV.Cp/GACV.Cp resolve through the family/scale criterion convention.

The resolver lowercases names and applies implemented extended-family and known-scale aliases. For extended families, predictive-score spellings outside their supported likelihood route can normalize to REML. A resolved string does not select an outer optimizer or certify convergence. Use :doc:`supports_smoothing_method` for its capability predicate and the fitting-support matrix for complete route restrictions.

Import: ``from nampy.gam.fit.selection import resolve_smoothing_method``. These are backend helper APIs; core-model methods remain the usual analysis interface.

Signature
---------

.. code-block:: python

   resolve_smoothing_method(model, method)

Parameters
----------

``model`` — Type: fitted core ``nampy.gam.GAM``
   Default: ``required``. Use a fitted core model, or ``estimator.gam_`` from a wrapper. Required compiled/fitted state is read from this object; passing a wrapper directly is not supported.

``method`` — Type: str | None
   Default: ``required (None is allowed)``. None or 'auto' selects a supported default. Strings are lowercased; GCV.Cp/GACV.Cp and likelihood spellings follow criterion normalization. Unsupported names raise ValueError.

Outputs
-------

``return value`` — Type: str, scalar
   Resolved method name. auto prefers available REML, then known-scale ubreaic, then GCV, then fixed. Extended-family predictive criterion spellings can normalize to reml; the result is a criterion name, not an optimizer or a completed fit.
